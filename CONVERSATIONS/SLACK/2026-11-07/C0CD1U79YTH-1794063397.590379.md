this message is on behalf of @Claude ai

I checked the prototype (`no-sql/numbers-as-formulas.md`, c748bd4c) against the event schema (`no-sql/the_porketo_db/trades.validator.json`) and `no-sql/DDD.md`. It mostly fits. Five things to settle before anyone approves it:

1. *Observed numbers aren't actually Decimal128 yet.* The note says receipt values are stored "digit for digit" as Decimal128. The validator still accepts `double` for `anchorUsdc`, `executionPrice`, `units`, `signedUnits`, `fee.qty` and `usdcEqCashFlow`. If that rule is meant seriously, those fields should be decimal only (int/long are fine too).
2. *`intended` isn't in the schema.* There's no `additionalProperties: false`, so Mongo would accept it, but it wouldn't be checked either. If it's approved, add `intended: { expr: string, value: decimal }`, nullable, on BUY/SELL.
3. *Entry price for the geometry should be `anchorUsdc / units`.* It shouldn't be parsed from `lotId`, because DDD §4 says the label is never parsed. Two reasons: `executionPrice` is in the native quote asset (e.g. the SPCXB buy paid in CVX), and the fee treatment differs between lots. The TSMB example already does it this way (2.25 / 0.00491341), so this is just a matter of making it the written rule.
4. *The threshold definitions don't match.* DDD §6 says `harvestThreshold = materialAnchor + targetProfit`, which is an absolute amount. The note uses `y = 1 + r`, which is a ratio. They're only the same if `targetProfit = r × anchor`. `protocols/harvest-ladder.md` should say which one we use.
5. *Partial SELLs aren't covered.* After a harvest, `y = value / anchor` needs a remaining-anchor rule: pro-rata, or the anchor stays the same per the "anchor immutable" invariant. Without that rule, harvested lots will plot in the wrong place.
θ and g staying computed in projections is consistent with DDD §6, so I see no conflict there. None of this changes the ledger yet. Booking in Mongo and the J-floor are still open.
